# 对照臂第 1 轮结果（2026-10-24）

## 怎么测的

- **三个案例**：问数、医嘱、慢愈患者端三份 README 的改前版本。每个案例跑两组：A 组不装 skill，B 组装 skill。一共 6 次，每组各跑 1 次。
- **两组条件相同**：同一个模型（Opus），同一句要求，各自一个隔离目录，目录里只有 README 和仓库文件清单。都不联网，都看不到答案和改后版本。B 组多了 SKILL.md、references 和 check.py。
- **答案事先冻结**：标准答案 `labels.json` 在跑之前就已提交（commit 3817f3b），之后没有改过。
- **计分人**：我自己（Claude）。标注、写 skill、计分都是同一个人，有偏向 B 组的风险。下面每一项判定都写明了依据，可以复核。

## 结果

| | A 不装 | B 装 skill |
|---|---|---|
| 核心问题找出（共 20） | **20／20** | **20／20** |
| 次要问题找出（共 6） | 6／6 | 5／6（问数漏了「贡献指南默认有代码」） |
| 报出的条数（三案例合计） | 92 | 62 |
| 其中属于本 skill 范围的（扣掉中性项） | 63／90，约七成 | 55／61，约九成 |
| 把核不动的外部事实判成「必须改」 | 1 次（慢愈 A #13：凭记忆断言 iPhone 17 Pro 改用了铝机身） | 0 次（同类事实都标了存疑或范围外） |
| 误把作者本人署名当成个人信息，停下不处理 | 1 次（医嘱 A #30） | 0 次 |
| 每条附证据位置、分三档判定 | 没有，只有「必须改／建议改」两档 | 有，并引用了 check.py 的结果 |
| 平均耗时、子代理 token | 约 105 秒、约 8.1 万 | 约 130 秒、约 9.2 万 |
| 违反流程 | 无 | 3 次都先跑了 `ls -R` 看目录，超出了「Bash 只跑 check.py」的约定（只读，不影响结果） |

**「范围外」怎么算**：设计点评、措辞润色、医疗规则建议、合规建议、遗漏提醒，这类意见不属于「说法和证据对不上」，都算范围外。逐条归类如下：

- A 组：问数 #9 #19 #23 #24 #26；医嘱 #14 #15 #18 #21 #22 #23 #24 #25 #30；慢愈 #10 #12 #24 #25 #26 #28 #29 #30 #31 #32 #33 #34 #35。
- B 组：问数 #25 #26；医嘱 #16 #18；慢愈 #17 #18。
- 中性项（拼写错误、口号）两组都不计：问数 A #1、B #1，医嘱 A #28。

## 结论

1. **按方案自己定的门槛，这一轮不过。** 方案里写的是：「装了 skill 比不装多找出的那部分，才是这个 skill 的价值；看不出差别就不发布。」结果两组的核心问题都是 20／20，找出的问题没有多一条。
2. **差别在别处。** 装了 skill 以后，报告收得更紧：条数少三分之一，九成以上都在范围内，每条有证据、分三档。核不动的外部事实一律标存疑，不会凭记忆就判「必须改」。不装 skill 也能找全，但会混进大量设计点评，还出了两次判断失误。
3. **为什么找出的问题一样多**：这三个案例对 Opus 来说太容易，属于天花板效应。而且六类问题本身就是从这三个案例里总结出来的，属于样本内测试，结果偏乐观。
4. **这一轮证明不了的**：
   - 换一个更小的模型，skill 能不能补上它漏掉的问题。
   - 拿这三个案例以外的文档测，skill 还管不管用。
   - 「更聚焦」是看完结果才找出的价值，属于事后改口径。要成立，必须事先定好指标，重新测一轮。
